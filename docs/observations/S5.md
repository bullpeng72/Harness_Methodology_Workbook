# 저자 관찰 — S5 (Gate C 정면돌파)

## RCA가 먼저 한 말 — C·D는 같은 원인

`agent-eval diagnose results/v1_run.json --baseline results/final/v0.json` (exit 0, HOTL):

```
Detected Gates: C, D
⚠ 2 Gates (C, D) detected simultaneously — don't assume a single cause too quickly.
[SLA shared-cause check] SLA breach/penalty detected — this may be a shared cause behind
  the simultaneous drop in Gate C and D. Investigate SLA-related changes first.
  sla_breach_rate=1.0 sla_window_penalty=0.3

Gate C — score 0.2000 (baseline 0.8000)
    sla_breach_count   0 -> 33   +33
Gate D — score 0.0000 (baseline 0.8881)
    p95_latency_s      0.0005 -> 15.2112
```

**Gate C가 0.20으로 떨어진 건 faithfulness가 아니라 SLA breach 100%였다.** v1의
`avg_llm_faithfulness`·`avg_reproducibility` 는 전부 `None`(측정 안 함). Gate C 공식은
`0.4×TCR(0.5) + 0.6×(SLA 등)` 인데 SLA breach 100%라 두 번째 항이 0에 가까움 → 0.20.

→ Ch 27(Gate C) 서사대로 "RAG + LLMJudge"부터 손대면 헛수고. **먼저 지연을 줄여야 한다** —
그게 C와 D의 공유 원인 (본편 §31.2, RCA 상호참조).

## S5 조치 (v2)

1. **LLM 호출 축소** (`pipeline.py`) — 지연 = 공유 원인.
   - 리뷰어: classifier confidence >= 0.80 이면 스킵 (단일 에이전트 경로). 불확실할 때만 v4 리뷰어+집계자.
   - 에스컬레이션: 환불·잠금 키워드 없으면 LLM 확인 없이 `escalate=None`.
   - 둘 다 정확도 축소가 아님 (고신뢰 분류·키워드 없는 티켓만 스킵).
2. **실제 임베딩 RAG** (`retriever.py`) — `mxbai-embed-large` 로 KB 인덱스 빌드(`data/kb/index.json`),
   쿼리 임베딩 + 코사인. 2-gram 폴백은 오프라인 경로로 유지.
3. **Gate C Config 활성** — `enable_hallucination_detection`(근거 대비, LLM 불필요) +
   `GracefulDegradationConfig`/`FaultToleranceConfig`/`IdempotencyConfig`.
4. **LLMJudge faithfulness** — Tier 1 키가 없어 이번엔 못 켬 (ADR-003: 채점은 Tier 1). 키 확보 시 재측정.

## 이 결과의 정직한 해석

- **되돌린 것**: v1이 만든 Gate C 회귀(0.20). v2에서 0.60. Gate G는 0.52→1.0 (실제 근거·인용).
- **아직 안 된 것**: C·D 둘 다 v0(0.80/0.89) 아래. 원인은 하나 — **SLA breach 100%**(p95 12.1s).
  이건 로컬 LLM으로 풀 파이프라인을 돌리는 한 남는다. **D를 고쳐야(S6) C도 완전히 회복**된다
  (RCA가 지목한 공유 원인).
- **교훈**: "Gate C를 고친다"가 실제로는 "공유 원인(SLA)을 고친다 + C 고유 성분을 측정한다" 두 가지였다.
  Ch 27을 "RAG+Judge"만으로 쓰면 이 구조를 놓친다.
